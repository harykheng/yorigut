# Ordi Master — Project Context

Repo master untuk generate deployment website pemesanan UMKM (F&B) buat klien Ordi. **React + Vite**, tiga aplikasi terpisah dalam satu repo (Vite multi-page app): katalog customer di `/`, dashboard admin di `/admin/`, lacak pesanan di `/tracking/`. Supabase dipakai sebagai database + auth + storage; hampir semua logic bisnis (QRIS, validasi promo, cek stok) jalan di browser atau lewat Postgres function. Dua pengecualian yang *wajib* backend: cek ongkir real-time (Biteship) lewat 1 Supabase Edge Function kecil (API key-nya secret), dan insert order + cek-status-pesanan lewat Postgres function (`place_order`/`lookup_order`) karena butuh atomicity/keamanan yang gak bisa dijamin dari browser doang — lihat bagian masing-masing di bawah. Tujuan desain: biaya operasional sekecil mungkin supaya cocok untuk skala UMKM.

Untuk setup/deploy/schema SQL, lihat `README.md`. File ini fokus menjelaskan **cara kerja tiap fitur** dan **di mana letak kodenya**, supaya sesi berikutnya tidak perlu re-explore dari nol.

Repo ini adalah copy dari codebase klien asli (Breva Coffee, toko kopi) yang sekarang jadi basis template multi-klien — kalau nemu sisa referensi "Breva" di suatu tempat, itu bug identitas yang harus dipindah ke env var, bukan hal yang disengaja (lihat "Kenapa begini" soal env var). Sebelum jadi React, repo ini vanilla HTML/CSS/JS (lihat git history sebelum commit rewrite), full-rewrite jadi React karena logic-nya sudah terlalu kompleks untuk dikelola manual lewat DOM manipulation. Business logic inti (QRIS EMV, Haversine, dsb) dipindah apa adanya dari versi vanilla — kalau ada keraguan soal behavior yang "benar", cek `src/shared/lib/` dulu.

**Status saat ini**: semua fitur F&B same-day (pickup/delivery + tanggal, ongkir Biteship, QRIS dinamis, stok, tracking, dashboard admin lengkap) sudah selesai dan ada di `main` — ini jadi base buat branch `tier-1`/`tier-2`/`tier-3` (WA-only / +ongkir / +QRIS). Konsep "tier-4" buat toko online umum (flow beda, kurir reguler kayak JNT, kemungkinan repo/branch terpisah) sempat dibahas tapi **ditunda**, fokus F&B dulu.

## Alur Customer (`src/customer/`)

State global order flow ada di `CartContext.jsx` (`useReducer`), diakses lewat `useCart()` di komponen manapun di dalam `<CartProvider>`. Field penting: `step` (1/2/3), `orderType`, `cart` (key = `productId` atau `productId|Var1|Var2` untuk kombinasi varian), `activePromo`, `selectedShipping`, `profile` (`name`/`wa`/`address`/`addressNote`/`lat`/`lng`), `note`, plus `shippingStatus`/`shippingOptions`/`shippingStaticKm` untuk hasil cek ongkir.

**Persistensi**: hanya `profile` yang disimpan ke `localStorage` (`ordi_customer_profile_v1`) — survive tutup browser total, supaya customer gak perlu isi ulang nama/WA/alamat tiap kunjungan. Cart, step, tanggal, promo, dan status ongkir **sengaja tidak** dipersist — refresh selalu balik ke step 1 kosong, biar gak ada cart/tanggal basi yang nyangkut berhari-hari. `RESET_ORDER` (dispatch setelah kirim bukti WA) mempertahankan `profile` tapi reset semua yang lain. Ini keputusan yang sempat berubah beberapa kali dalam pengembangan — kalau mau ubah lagi, baca dulu komentar di `CartContext.jsx`.

### Step 1 — `OrderTypeStep.jsx`
Pilih pickup/delivery + tanggal (chip 7 hari dari `buildDateChips()` di `shared/lib/format.js`). Dispatch `SELECT_ORDER_TYPE`/`SET_DATE`, lanjut lewat `SET_STEP`. Footer ada link **"📦 Lacak Pesanan"** ke `/tracking/`.

### Step 2 — `CatalogStep.jsx` + `ProductCard.jsx` + `VariantSheet.jsx`
- `useProducts({ onlyVisible: true })` ambil dari tabel `products` (RLS sudah filter `is_visible=true` juga, filter di query cuma optimisasi).
- Produk tanpa varian: qty stepper langsung (dispatch `SET_CART_QTY`). Produk dengan varian: buka `VariantSheet` (state lokal `selected`/`qty`, konfirm dispatch `ADD_TO_CART` dengan `cartKey` gabungan label varian).
- Cart math (`cartCount`, `cartTotal`, `getDiscountAmount`, `cartFinalTotal`, `getProductCartQty`, `cartStockItems`) semua pure function di `shared/lib/cart.js` — dipanggil dengan `state.cart` sebagai parameter, bukan baca state global langsung.
- **Stok** (`product.stock_qty`, `NULL` = tak terbatas): kalau 0, `ProductCard` nampilin badge "Habis" + disable semua kontrol. Kalau terbatas, qty stepper di-cap ke sisa stok (dikurangi qty yang udah di cart), dan `VariantSheet` cap qty-nya juga berdasarkan total qty lintas-varian produk yang sama (stok dilacak per-produk, bukan per-varian).
- **Cart bar** (`catalog-sticky-footer`) bisa di-tap buat expand ke atas, nampilin list item + qty + subtotal per item — bukan cuma badge total doang.

### Step 3 — `CheckoutStep.jsx`
- **Kartu Profil**: tap buka `ProfileModal` (di-render selalu di `App.jsx`, toggle via `isOpen` prop — bukan mount/unmount, supaya form state persist antar buka-tutup).
- **Alamat**: bukan field teks langsung di dalam `ProfileModal` — field-nya cuma kartu ringkasan (`address-summary-card`, atau tombol placeholder `address-summary-empty` kalau kosong) yang tap-nya buka `AddressPickerModal.jsx`, full-screen overlay 2 step: **search** (input full-screen, autofocus, hasil dari LocationIQ REST API `fetch` biasa) → **confirm** (peta lebih besar via `AddressMapPreview` prop `large`, plus field "Catatan Alamat"). Baru pas tap "Simpan Alamat Ini" koordinat+alamat+catatan dilaporkan balik ke `ProfileModal` lewat `onConfirm`, ProfileModal sendiri gak pernah manggil LocationIQ langsung. `AddressPickerModal` di-render sebagai sibling dari `.profile-sheet` di dalam `.profile-overlay` (yang punya `onClick={onClose}` buat close-on-backdrop) — **wajib** `onClick={(e) => e.stopPropagation()}` di root overlay-nya, kalau kelewat, tap apapun di dalam picker bakal ke-bubble dan nutup seluruh `ProfileModal` (bukan cuma picker-nya) — bug ini pernah kejadian beneran, lihat "Kenapa begini".
- **Ongkir**: `useShipping().calculate(lat, lng, weightGrams, orderValue)` punya DUA titik panggil, keduanya "fire once", bukan `useEffect` yang watch perubahan alamat (itu justru bug yang mau dihindari, lihat "Kenapa begini" di bawah): (1) handler save di `ProfileModal.jsx` — tiap kali customer simpan/ubah alamat; (2) `CheckoutStep.jsx`'s mount effect (deps `[]`) — auto-trigger saat customer *masuk* ke step 3 kalau `state.profile.lat/lng` udah ada (returning customer, alamat ke-restore dari `localStorage`) DAN `shippingStatus` masih `'idle'` (belum pernah dihitung sesi ini), biar gak perlu buka-tutup `ProfileModal` cuma buat lihat ongkir. Karena `CheckoutStep` unmount/remount tiap ganti step (lihat `App.jsx`'s `state.step === 3 && <CheckoutStep .../>`), efek ini otomatis re-armed tiap customer balik lagi ke step 3 — tapi guard `shippingStatus === 'idle'` mencegah re-fetch kalau udah ada hasil. Hasilnya dispatch ke `CartContext` (`SET_SHIPPING_OPTIONS`/`SET_SHIPPING_STATIC`/`SET_SHIPPING_UNAVAILABLE`), ditampilkan `OngkirOptions.jsx` yang render di `CheckoutStep` (bukan di dalam modal profil) — termasuk state `'loading'`-nya, jadi auto-check dari titik (2) gak butuh overlay terpisah. Koordinat resolved disimpan balik ke `state.profile.lat/lng` juga (bukan cuma state lokal `ProfileModal`), supaya map pin & hasil ongkir bisa dipulihkan kalau modal ditutup-buka lagi.
  - `useShipping.js` cuma punya SATU jalur: `checkBiteshipRatesViaEdgeFunction()` → `supabase.functions.invoke('check-shipping')`. Tidak ada jalur "panggil Biteship langsung dari browser".
  - **Fallback**: kalau Edge Function gagal/error/kosong, otomatis `haversineDistance()` + `calcShippingRate(km)` dari `shared/lib/shipping.js` (≤3km=Rp8rb, ≤6km=Rp15rb, ≤10km=Rp22rb, >10km=`SET_SHIPPING_UNAVAILABLE`).
  - **Loading state**: selama `calculate()` berjalan, `ProfileModal.jsx` set `saving=true` yang me-render `ShippingLoadingOverlay.jsx` via `createPortal` ke `document.body`.
  - **Guard sebelum bayar**: `App.jsx`'s `handleSubmitQris()` block submit (toast error, gak buka QrisModal) kalau `orderType === 'delivery'` dan belum ada `selectedShipping` (ongkir belum ke-calculate) atau `shippingStatus === 'unavailable'` (di luar jangkauan) — mencegah order delivery ke-submit tanpa `shipping_cost`.
- **Promo**: `fetchActivePromoByCode()` (`shared/lib/promos.js`) query `promo_codes` by `code` + `is_active=true`, cek `min_order`. Hasil dispatch `APPLY_PROMO`.

### Pembayaran QRIS — `QrisModal.jsx`
- Snapshot order (`pendingOrder`, termasuk `stockItems` dari `cartStockItems()`) dibuat di `App.jsx`'s `handleSubmitQris()` — bukan di dalam `QrisModal` sendiri, supaya validasi profil/ongkir bisa jalan sebelum modal kebuka.
- `qrisToDynamic(QRIS_STATIC, amount)` dari `shared/lib/qris.js` — inject nominal ke payload EMV + hitung ulang CRC16. **Deterministik**: input sama selalu hasilkan string sama, QR bisa digenerate ulang kapan saja tanpa expiry.
- QR dirender ke `<canvas>` pakai package `qrcode` (`QRCode.toCanvas()`).
- Konfirmasi → `insertOrder()` (`shared/lib/orders.js`) — **bukan insert langsung**, tapi lewat `supabase.rpc('place_order', { order_data, stock_items })` (lihat bagian "Stok & `place_order()`" di bawah). Kalau gagal karena stok abis, error message-nya diawali `STOK_HABIS:` dan ditangkap khusus buat toast yang lebih jelas + modal ditutup (bukan pesan generik).
- Sukses → `onConfirmed` callback ke `App.jsx` → buka `OrderSummaryModal`.

### Ringkasan Pesanan — `OrderSummaryModal.jsx`
- Kode pesanan, rincian pengiriman (termasuk alamat toko), item & total.
- Kartu kode pesanan juga ada link **"Simpan kode ini buat lacak status pesanan kapan aja"** ke `/tracking/?order=<kode>`.
- "Kirim Bukti Transfer via WA" buka `order.waUrl` (link `wa.me` dibangun di `QrisModal` pakai `buildQrisConfirmMessage()` dari `shared/lib/whatsapp.js`), lalu dispatch `RESET_ORDER`.
- **"Tampilkan QR lagi"** — buka `QrisViewModal.jsx`, popup read-only (cuma QR + total + tombol simpan gambar) yang stack di atas `OrderSummaryModal` via state lokal, **BUKAN** navigasi balik ke `QrisModal` penuh. Sengaja gak ada tombol "Konfirmasi Pesanan" di situ — order-nya udah ke-insert sekali, kalau reshow lewat `QrisModal` lagi (versi lama), tombol konfirmasi masih aktif dan bisa ke-klik ulang → coba insert `order_number` yang sama → error unique constraint. Jangan balikin ke pola lama itu.

## Alur Tracking (`src/tracking/`)

Halaman standalone (`/tracking/`), gak ada CartProvider/state global — cuma form lookup: kode pesanan + nomor WhatsApp pemesan. Prefill kode via query param `?order=<kode>` kalau datang dari link `OrderSummaryModal`.

- `lookupOrder(orderNumber, customerWa)` di `shared/lib/orders.js` manggil `supabase.rpc('lookup_order', { p_order_number, p_customer_wa })` — **bukan** `SELECT` langsung, karena `orders` RLS sengaja insert-only untuk `anon` (privasi data pelanggan lain). Function ini (definisi di `supabase-setup.sql` §7) cuma balikin 1 row kalau **kode DAN nomor WA cocok berbarengan**; `SECURITY DEFINER` biar bisa baca tabel tanpa buka policy SELECT publik yang bisa di-scan buat ngintip semua pesanan.
- `OrderStatusCard.jsx` render status (`ORDER_STATUS_LABELS` dari `whatsapp.js`, sama persis kayak yang admin lihat), item, alamat/kurir kalau delivery, dan rincian total.
- Gak ketemu → pesan "Pesanan tidak ditemukan", gak dibedain apakah kode salah atau WA salah (sengaja, biar gak jadi celah buat nebak-nebak kode pesanan orang lain).

## Alur Admin (`src/admin/`)

`AuthContext.jsx` wrap Supabase Auth session. `App.jsx` render `LoginScreen` kalau `session` null, `Dashboard` kalau ada session — hanya user yang dibuat manual di Supabase Dashboard yang bisa masuk, dua cara: **Create new user** (isi password langsung, siap pakai) atau **Invite user** (kirim link ke email) — lihat README §1 "Buat Akun Admin". `Dashboard` juga pasang `useNewOrderAlerts()` (selalu mounted selama login, independen dari tab mana yang aktif) dan render tab bar yang **scrollable horizontal** (`overflow-x: auto` di `.admin-tabs`) — ini bukan kosmetik, tanpa itu 5 tombol tab overflow dan bikin **seluruh halaman** ke-scroll horizontal di layar HP (root cause dari bug "admin versi mobile berantakan").

**Invite-link flow** (`SetPasswordScreen.jsx`) — link undangan Supabase redirect balik ke `/admin/` dengan token di URL (`#access_token=...&type=invite`, hash buat implicit flow lama / query string buat PKCE) yang otomatis dibaca `supabase-js` jadi session valid. `AuthContext.jsx`'s `detectPasswordSetupType()` baca `type=invite`/`type=recovery` langsung dari `window.location` (bukan dari nama event `onAuthStateChange`, yang gak konsisten antara invite vs recovery link) buat nentuin kapan nampilin `SetPasswordScreen` alih-alih `LoginScreen`/`Dashboard` — exposed sebagai `needsPasswordSetup` di context. Di dalam `SetPasswordScreen`: kalau session ada (token valid) → form set password (`supabase.auth.updateUser({ password })`), submit sukses manggil `completePasswordSetup()` yang strip URL params (`history.replaceState`) biar refresh gak nampilin form ini lagi; kalau session `null` (link expired/udah dipakai/invalid) → pesan error, bukan form kosong. **Wajib** set Site URL/Redirect URLs di Supabase Dashboard (Authentication → URL Configuration) ke domain admin kamu, kalau enggak Supabase nolak redirect-nya duluan sebelum sempat ke halaman ini.

### Tab Dashboard — `DashboardTab.jsx`
Tab default saat login. Sebagian besar angka dihitung client-side di `useMemo` dari `useOrders()` (tidak ada tabel/agregasi baru di Supabase untuk order) — cuma status `confirmed`/`done` yang dihitung sebagai "revenue" (`REVENUE_STATUSES` di `DashboardTab.jsx`), `pending` sengaja dikecualikan karena itu baru "customer klaim udah bayar", belum diverifikasi admin dari bukti transfer; `cancelled` juga dikecualikan. Kartu: pendapatan/pesanan/item terjual hari ini, omset bulan berjalan. Chart batang 7 hari terakhir dan daftar produk terlaris bulan ini dibangun pure CSS/JS (tanpa charting library) — data qty/revenue per produk diambil dari field `nm`/`qty`/`sub` di `orders.items` (shape yang sama dipakai `cartSnapshot()`, lihat `shared/lib/cart.js`).

**Pengunjung** — beda dari angka lain di tab ini, ini SATU-SATUNYA agregasi yang dihitung di database, bukan client-side dari `useOrders()`, karena `anon` tidak boleh baca tabel `orders`. Tabel `daily_visits` (satu baris counter per tanggal, lihat `supabase-setup.sql` §12) di-upsert lewat `track_visit()` yang dipanggil `src/customer/App.jsx` sekali per sesi tab (guard `sessionStorage`, bukan tiap render/refresh — biar gak inflate angka). `useDailyVisits()` (dipakai `DashboardTab.jsx`) baca 7 hari terakhir buat kartu "Pengunjung Hari Ini" + chart batang, pola render sama persis kayak chart pendapatan di atasnya.

### Tab Produk — `ProductsTab.jsx` + `ProductFormModal.jsx` + `ProductImportModal.jsx`
- CRUD ke tabel `products` lewat `saveProduct()`/`deleteProduct()` (`shared/lib/products.js`, termasuk upload foto ke bucket `product-images`, dan field `stock_qty` opsional — kosong berarti tak terbatas).
- Varian dikelola sebagai array-of-objects local state (`variantGroups`) di form, diserialize ke JSON pas submit.
- **Import CSV**: `ProductImportModal.jsx` parse file pakai `parseCsvObjects()` (`shared/lib/csv.js`, hand-rolled RFC4180-ish parser — bukan library), validasi tiap row (nama/harga/stok), preview mana yang valid vs dilewati (dengan alasan), baru `importProducts()` bulk-insert. Foto & varian gak bisa lewat CSV (gak representable di format flat), harus ditambah manual lewat Edit setelah import.

### Tab Promo — `PromoTab.jsx` + `PromoFormModal.jsx`
CRUD ke `promo_codes` lewat `savePromo()`/`deletePromo()`. Tipe diskon `percent` atau `flat`, opsional `min_order` dan `expires_at`.

### Tab Pesanan — `OrdersTab.jsx` + `OrderDetailModal.jsx` + `PrintLabel.jsx`
- `useOrders()` ambil semua row `orders` (RLS: hanya `authenticated` boleh SELECT), filter client-side pesanan `pending` yang sudah lewat 24 jam (disembunyikan dari list, bukan dihapus).
- Filter status via tab: `pending` (default) → `confirmed` → `done`, atau `cancelled`.
- `OrderDetailModal` aksi: **Konfirmasi/Selesai/Batalkan** → `updateOrderStatus()`; **Print Label** → `window.print()` (lihat catatan portal di bawah); **WA Customer** → `buildAdminOrderSummaryMessage()` (`shared/lib/whatsapp.js`) buka `wa.me/{customer_wa}` terisi otomatis.
- **`PrintLabel.jsx` pakai React Portal** (`createPortal`) ke `#printLabel`, `<div>` direct child `<body>` di `admin/index.html` (bukan di dalam `#root`) — CSS `@media print` di `admin.css` pakai selector `body > *:not(#printLabel)`. Kalau `#printLabel` dipindah ke dalam tree React normal, print CSS-nya rusak.
- **Export CSV** — `downloadCsv()` (`shared/lib/csv.js`, hand-rolled: proper escaping koma/kutip + BOM prefix biar Excel buka UTF-8 dengan benar) export list yang lagi ke-filter di tab.
- **Notifikasi live** — `useNewOrderAlerts.js` (`src/admin/hooks/`) subscribe Supabase Realtime `postgres_changes` INSERT di tabel `orders` (butuh `ALTER PUBLICATION supabase_realtime ADD TABLE orders`, ada di `supabase-setup.sql` §6). Toast + beep (Web Audio API, gak ada file audio) + badge angka di tab "Pesanan", cleared pas admin klik ke tab itu. **In-tab only** — bukan push notification asli ke HP (butuh service worker + Web Push infra, di luar scope), dan Realtime tetap tunduk RLS jadi `anon` gak pernah dapet event ini.

### Tab Pengaturan — `SettingsTab.jsx`
Form yang upsert ke tabel `settings` (row `id=1`) lewat `saveSettings()` (`shared/lib/settings.js`): nama/ikon/logo brand, nomor WhatsApp admin, alamat & jam toko, link Maps, banner katalog, link Instagram/TikTok. Upload logo & banner lewat bucket `product-images`.

**Nomor WhatsApp admin** (`settings.admin_whatsapp`) — dulu cuma bisa di-set lewat env var `VITE_ADMIN_WHATSAPP` (butuh redeploy tiap ganti nomor), sekarang bisa diganti kapan aja dari section "Kontak" di tab Pengaturan tanpa redeploy. Input di-filter otomatis ke digit doang (`replace(/[^\d]/g, '')`) biar formatnya konsisten (`62` + nomor tanpa `0` di depan, sama kayak format env var-nya). Dipakai di 3 tempat, semua dengan pola fallback `settings?.admin_whatsapp || config.adminWhatsapp` (env var jadi fallback kalau admin belum pernah isi dari Pengaturan): tombol "Butuh Bantuan" di `OrderTypeStep.jsx`/`CatalogStep.jsx`, dan tujuan "Kirim Bukti Transfer via WA" di `QrisModal.jsx` (yang perlu prop `settings` diteruskan dari `App.jsx`, beda dari komponen lain yang udah dapet `settings` dari awal).

**Brand header punya 2 slot gambar independen**, bukan satu "logo" — `logo_url` (logo ikon/mascot, gantiin emoji `brand_icon` di slot kecil) dan `logo_text_url` (logo teks/wordmark, gantiin tulisan `brand_name` di sebelahnya). Keduanya opsional dan independen: admin bisa pasang cuma salah satu, dua-duanya, atau gak sama sekali (fallback ke emoji+teks polos). Dirender di `OrderTypeStep.jsx` dan `CatalogStep.jsx` — tiap slot punya CSS class sizing sendiri (`brand-icon-logo` buat logo ikon, `ob-brand-name-logo`/`topbar-brand-name-logo` buat logo teks), jangan ketuker kalau nambah tempat baru yang nampilin brand header. `brand_name` (teks) tetap dipakai apa adanya di tempat non-visual (judul tab browser, pesan WA, dsb) — cuma tampilan header customer yang bisa diganti gambar.

**Favicon** (`settings.favicon_url`) — upload sendiri di section "Favicon" tab Pengaturan, disimpan ke bucket `product-images` kayak logo/banner (lihat `uploadSettingsImage()` di `shared/lib/settings.js`). Beda dari logo/banner yang di-render langsung sebagai `<img>` di JSX, favicon itu `<link rel="icon">` di `<head>` — gak bisa diubah cuma dengan render ulang komponen React, makanya ada `shared/components/FaviconSync.jsx`: komponen tanpa UI (`return null`) yang manggil `useSettings()` sendiri dan, kalau `favicon_url` ada, hapus semua `<link rel="icon">` static dari `index.html` lalu suntik satu yang baru nunjuk ke URL upload-an. Di-mount sekali di root tiap app (`customer/App.jsx`'s `AppShell`, `admin/App.jsx`'s `AppShell` — sebelum cek session biar kepakai juga di `LoginScreen`, dan `tracking/App.jsx`). Kalau `favicon_url` kosong (belum pernah upload / tabel `settings` belum ada), efeknya no-op dan favicon default dari `public/` (link di `index.html`) yang kepake — gak ada fallback ganda yang perlu di-manage.

`useSettings()` (hook yang sama dipakai lintas app) di-consume `src/customer/App.jsx` buat baca `settings` sekali di top level dan diteruskan sebagai prop `settings` ke tiap step. Kalau tabel `settings` belum dibuat/kosong, hook fail silent dan komponen fallback ke `config.js` (`shared/lib/config.js`, baca env var `VITE_*`).

## Stok & `place_order()`

`products.stock_qty` (`NULL` = gak dilacak/selalu tersedia). Checkout **tidak pernah** insert langsung ke `orders` — selalu lewat `supabase.rpc('place_order', { order_data, stock_items })` (definisi di `supabase-setup.sql` §6, `src/shared/lib/orders.js`'s `insertOrder()`). Alasannya WAJIB backend, bukan gaya-gayaan: cek-lalu-kurangi stok dari browser (read stok → cek cukup → insert order) punya race condition kalau 2 customer checkout produk yang sama nyaris bersamaan — dua-duanya bisa lolos cek sebelum salah satu sempat nulis hasil kurangnya, jadi oversell.

`place_order()` jalan sebagai satu transaksi Postgres: tiap item di `stock_items` dikurangi dari `stock_qty` HANYA kalau cukup; begitu ada satu item gagal, **seluruh transaksi rollback** (termasuk item lain yang sempat kepotong di iterasi sebelumnya) dan order gak jadi ke-insert — customer dapet toast `STOK_HABIS: <nama produk> stoknya tidak cukup`. `SECURITY DEFINER` biar function ini bisa UPDATE `stock_qty` walau `anon` sengaja gak dikasih policy UPDATE langsung ke `products`.

Sudah pernah divalidasi langsung ke Postgres lokal (bukan cuma dibaca): order normal, stok kurang → block+rollback, produk unlimited (NULL) gak pernah kepotong, order multi-item yang salah satu itemnya gagal → semua item ikut rollback.

## Keputusan Desain / "Kenapa begini"

- **Full-rewrite dari vanilla JS ke React** — business logic (ongkir Biteship+fallback, QRIS, autocomplete alamat, stok, admin CRUD) sudah terlalu banyak untuk dikelola lewat manual DOM manipulation. Vite dipilih (bukan Next.js) supaya tetap static site, tanpa SSR, tanpa backend baru selain Edge Function/Postgres function yang memang wajib.
- **Vite multi-page app (tiga entry point), bukan satu SPA + React Router** — customer, admin, dan tracking nyaris tidak share UI (cuma shell modal/button generik + beberapa class CSS), dan model data/auth-nya beda-beda (admin butuh login, tracking butuh lookup sempit, customer publik penuh). Entry terpisah bikin bundle lebih kecil (masing-masing gak pernah download kode dua yang lain) tanpa perlu routing library. Tracking sengaja dibikin entry terpisah, bukan halaman di dalam SPA customer, karena butuh URL yang bisa di-share/bookmark dan gak ada hubungannya sama state cart/order flow sama sekali.
- **State management: `useReducer` + Context, bukan Zustand/Redux** — state customer (cart, orderType, promo, shipping, profile) itu banyak tapi gak kompleks, cukup satu `CartContext` per app-lifetime. Admin gak butuh state global sama sekali — tiap tab punya state lokal sendiri, cuma `AuthContext` yang global.
- **Persist profile ke `localStorage`, TAPI cart/step/tanggal sengaja TIDAK dipersist** — awalnya sempat dicoba persist SEMUA state order ke `sessionStorage` (biar refresh gak hilang), tapi user cuma mau bagian profil doang yang nempel lama (survive tutup browser, bukan cuma refresh), sementara cart/tanggal harus selalu fresh tiap kunjungan biar gak ada pesanan basi nyangkut. Kalau nanti ada permintaan "cart juga jangan hilang", diskusikan dulu soal staleness (harga berubah, stok abis, promo expired, tanggal "hari ini" jadi gak relevan) sebelum asal nyalain persist lagi.
- **CSS tidak ditulis ulang** — file CSS lama (`main.css`/`catalog.css`/`admin.css`) di-import apa adanya sebagai global stylesheet, semua class name JSX match 1:1 sama markup lama. `tracking.css` adalah pengecualian (halaman baru, gak ada padanan vanilla) tapi tetap reuse var/class yang ada semaksimal mungkin (`.catalog-topbar`, `.co-item`, dst) daripada duplikasi.
- **Client-side by default, backend hanya kalau benar-benar wajib.** QRIS dan promo client-side supaya tidak ada biaya API per-transaksi. Pengecualian yang WAJIB backend ada 3, masing-masing dengan alasan teknis yang beda:
  1. **Ongkir (Edge Function `check-shipping`)** — Biteship API key secret, gak bisa dibatasi per-domain kayak LocationIQ.
  2. **`place_order()`** — butuh atomicity (cek+kurangi stok) yang gak bisa dijamin dari browser, bukan soal secret.
  3. **`lookup_order()`** — butuh narrow query (cuma 1 row kalau kode+WA cocok) yang gak bisa diekspresikan sebagai RLS policy tanpa membuka SELECT publik ke seluruh tabel.
- **Debounced single-ongkir-check-on-save dipertahankan ketat** — `useShipping().calculate()` cuma boleh dipanggil dari titik yang "fire once", bukan dari `useEffect` yang watch perubahan alamat/koordinat. Godaan paling gampang adalah nulis `useEffect(() => { calculate(...) }, [address])` yang kelihatan lebih "React-idiomatic" — itu salah, bakal manggil Biteship berkali-kali tiap customer ngetik. Ada dua titik panggil yang sah (lihat "Ongkir" di atas): `ProfileModal`'s save handler (tiap kali alamat disimpan), dan `CheckoutStep`'s mount effect dengan deps `[]` + guard `shippingStatus === 'idle'` (auto-check pas masuk checkout kalau alamat udah ke-restore dari profil tersimpan). Keduanya beda dari pola terlarang di atas karena depsnya bukan `[address]`/`[lat, lng]` — gak ada yang re-run tiap koordinat berubah.
- **Ongkir dicoba Biteship dulu, baru fallback ke Haversine + tarif flat per tier** kalau Biteship/Edge Function gagal.
- **Daftar `couriers` yang diminta ke Biteship di-hardcode di `check-shipping/index.ts`** (`couriers: 'gosend,grab,paxel'`) — kalau mau nambah/kurangi kurir yang ditawarkan (mis. tambah `jne`/`sicepat` buat delivery jarak jauh), edit string ini, bukan cuma andelin default Biteship. Biteship cuma balikin tarif buat kurir yang (a) ada di list ini, DAN (b) aktif/terverifikasi di akun Biteship kamu (dashboard Biteship, bukan kode) — jadi kalau habis nambah kurir ke list tapi tarifnya tetap gak muncul, curigai dulu status aktivasi kurir itu di dashboard Biteship, bukan bug di Edge Function.
- **Maps hanya link share statis + Leaflet/OpenStreetMap buat preview pin**, bukan Google Maps JavaScript API — supaya tidak kena biaya Maps API. Leaflet dipilih spesifik karena free tile server (OSM), gak butuh API key sama sekali — beda dari kalau pakai Google/Mapbox yang based-billing.
- **LocationIQ dipakai khusus untuk autocomplete alamat** (bukan hitung jarak) — tier gratisnya cukup untuk skala UMKM. Hasil pencarian di-bias ke area toko lewat parameter `viewbox` (kotak ~55km di sekitar `config.storeLat`/`storeLng`) + `bounded=0` di `fetchSuggestions()` (`AddressPickerModal.jsx`) — soft bias, bukan hard filter, jadi nama tempat yang sama di kota lain (mis. "Taman Anggrek" di Jakarta vs Bandung) gak nongol duluan cuma karena rank default LocationIQ, tapi hasil di luar kotak tetap bisa muncul kalau memang gak ada match lokal. Sengaja bukan `bounded=1` (hard filter) — kalau radius kotaknya kurang pas buat suatu toko, `bounded=1` bisa nge-hide alamat yang bener sama sekali. Di atas bias itu, hasil di-sort ULANG secara eksplisit pakai `haversineDistance()` (`shared/lib/shipping.js`, fungsi yang sama dipakai fallback ongkir) supaya urutannya dijamin dari yang paling deket ke toko — `viewbox` sendiri cuma ngubah ranking relevansi internal LocationIQ (campuran text-match + proximity), bukan jaminan urutan jarak asli.
- **QRIS statis → dinamis dilakukan di browser**, bukan lewat payment gateway — supaya tidak ada biaya transaksi. Trade-off: admin harus verifikasi manual dari bukti transfer via WA. "Tampilkan QR lagi" sengaja dibikin popup read-only (`QrisViewModal`) yang gak punya tombol konfirmasi, bukan reshow `QrisModal` yang asli — biar gak ada jalan buat re-trigger insert order yang sama dua kali.
- **`orders` RLS insert-only untuk anon** — customer gak pernah butuh SELECT langsung ke tabel ini. Cek status pesanan (`/tracking/`) lewat `lookup_order()` yang sempit, bukan buka policy SELECT.
- **Notifikasi admin lewat Supabase Realtime, in-tab only** — bukan push notification asli (butuh service worker + Web Push, di luar scope "client-side by default"). Ini keputusan sadar buat jaga kompleksitas tetap rendah, bukan keterbatasan yang gak disengaja.
- **CSV import/export hand-rolled, bukan library** — format-nya cukup simpel (quote/escape/BOM) buat ditulis sendiri tanpa nambah dependency.
- **Admin tab bar scrollable horizontal, bukan wrap ke bawah** — root cause bug "mobile berantakan" sebelumnya adalah tab bar yang overflow diam-diam dan narik seluruh halaman ke-scroll horizontal (elemen `position:fixed` kayak modal jadi kelihatan salah posisi relatif ke konten yang udah melebar). Fixnya bikin tab bar-nya sendiri yang scroll (`overflow-x:auto`, `flex-shrink:0` per tab), pola standar mobile tab bar.
- **Vite 8 wajib** — Cloudflare's Workers deploy flow butuh Vite ≥6 supaya bisa auto-configure project.
- **`wrangler.jsonc` ada karena Cloudflare dashboard sekarang default ke alur "Workers"** — mendeklarasikan deploy sebagai static-assets-only (`assets.directory: "./dist"`) supaya Wrangler skip parsing `vite.config.js` (yang bakal gagal karena multi-entry).
- **Skema RLS kanonik di README bisa drift dari yang live di Supabase** — pernah kejadian tabel `orders` di production cuma punya policy admin (ALL), **tanpa** `"Public insert orders"` untuk `anon`, jadi semua checkout customer gagal `42501`. Juga pernah kejadian storage policy `product-images` cuma punya INSERT+DELETE, kelewat SELECT+UPDATE (yang terakhir dibutuhkan spesifik buat upload `upsert:true` di SettingsTab). Kalau ada laporan bug "gagal insert/upload" yang tidak masuk akal dari sisi kode, curigai dulu RLS drift — diagnosis lewat `SELECT policyname, cmd, roles FROM pg_policies WHERE tablename = '<table>';`, bandingkan ke `supabase-setup.sql` (bukan cuma README), baru simpulkan itu bug kode atau schema yang belum disinkron.
- **Paste secret (Biteship key, dsb) ke textarea dashboard bisa menyisipkan newline literal tanpa terlihat** — gejalanya Edge Function selalu gagal dengan `TypeError: Invalid header value`, bukan error auth biasa.
- **`supabase-setup.sql` adalah sumber kebenaran skema, README dokumentasi turunannya** — kalau bikin perubahan schema/function/policy, edit `supabase-setup.sql` dulu (idempotent, `DROP POLICY IF EXISTS`/`CREATE OR REPLACE FUNCTION`/`ADD COLUMN IF NOT EXISTS` semua dipakai supaya aman di-re-run di instance yang udah jalan), baru sinkronkan ke README. Jangan tulis SQL cuma di README doang.
- **Alamat delivery dipindah dari dropdown-in-sheet (`AddressAutocomplete.jsx`, sudah dihapus) ke full-screen picker (`AddressPickerModal.jsx`)** — dropdown suggestion yang nempel di textarea kecil di dalam bottom sheet konsisten kena masalah di mobile: ketutup keyboard, harus scroll manual buat lihat hasil, dan kalau alamat udah ke-resolve sebelumnya (edit ulang), dropdown-nya bisa tabrakan sama `AddressMapPreview` (Leaflet punya internal z-index sampai 800 di stacking context global, gampang ngalahin dropdown manapun). Full-screen picker (2 step terpisah: search lalu confirm) ngilangin semua masalah itu sekaligus — gak ada lagi yang perlu di-scroll-into-view atau di-z-index-perang-in, karena search dan map gak pernah tampil bersamaan di layar yang sama.
- **Demo badge tier di customer app (`TierBadge.jsx`/`TierCompareModal.jsx`, `config.demoMode` dari `VITE_DEMO_MODE`) — sengaja CUMA ada di `main`, JANGAN di-merge/cherry-pick ke `tier-1`/`tier-2`/`tier-3`.** `main` gabung semua fitur 3 tier jadi satu build, dipakai buat demo jualan ke calon klien — badge kecil ("🚚 Antar"/"💳 Bayar") di fitur-fitur yang beda per paket, klik buka tabel perbandingan Basic/Antar/Bayar. Default off (`VITE_DEMO_MODE` gak di-set = badge gak pernah render), biar aman kalau ada yang gak sengaja pakai `main` buat build client asli. Deployment client sungguhan selalu dari salah satu `tier-1`/`tier-2`/`tier-3`, yang emang cuma punya fitur 1 tier — badge perbandingan gak relevan di situ.
